# MGS Pricing — การแจ้งเตือน Lark (v4.9 · webhook แยกกลุ่ม + กลุ่มคำขอราคา)

รอบนี้ **ยังไม่ส่งเข้ากลุ่มจริง** ระบบสร้างข้อความครบทุก event แล้วเก็บไว้ในแท็บ `NotifyQueue` (Status = `DRYRUN`) ให้ตรวจก่อน
เปิดส่งจริงเมื่อพร้อม โดยเปลี่ยน Script Property `LARK_MODE` เป็น `live` (ไม่ต้องแก้โค้ด)


## 0. ตั้งค่าแบบง่ายด้วย webhook (v4.9) — แนะนำสำหรับเริ่มใช้

### กลุ่มที่ควรสร้างใน Lark
| กลุ่ม Lark (ตัวอย่างชื่อ) | สมาชิก | Script Property (webhook) | ได้รับ |
|---|---|---|---|
| **MGS คำขอราคา** | Sales ทุกคน + Sourcing | `LARK_WEBHOOK_REQUESTS` (+ `_SECRET`) | SR ใหม่ · ปล่อยราคาแล้ว — **ไม่มียอดเงิน/GP** |
| **MGS ผู้อนุมัติราคา** | Procurement Mgr · BD Mgr · GM เท่านั้น | `LARK_WEBHOOK_APPROVERS` (+ `_SECRET`) | ใบรออนุมัติ (มี %GP) · งานรออนุมัติเกินกำหนด · สรุปเช้า |
| **MGS Sourcing** *(ทางเลือก)* | ทีม Sourcing เท่านั้น | `LARK_WEBHOOK_SOURCING` (+ `_SECRET`) | อนุมัติครบ / ส่งกลับแก้ (มียอดเงิน) · งานเกินกำหนด · สรุปเช้า |
| **MGS ทีมขาย** *(ทางเลือก)* | Sales + Sales Manager | `LARK_WEBHOOK_SALES` (+ `_SECRET`) | ปล่อยราคาแล้ว · อนุมัติครบรอปล่อย (ถึงผู้ปล่อยราคา) · งานค้างอัปเดต — ไม่มียอดเงิน |

- ตั้งแค่บางกลุ่มก็ได้ — กลุ่มที่ไม่ตั้งจะถูกข้าม (คิวบันทึกว่า SKIPPED)
- ถ้าใช้กลุ่ม **MGS คำขอราคา** กลุ่มเดียวแทนกลุ่ม Sourcing (ตั้ง `LARK_WEBHOOK_SOURCING` เป็น URL เดียวกัน) ระบบจะ **ไม่ส่ง** ข้อความภายในที่มียอดเงินเข้ากลุ่มนั้น (ระงับอัตโนมัติ) — SR ใหม่ยังเข้ากลุ่มครั้งเดียว
- **กติกาความปลอดภัย:** กลุ่มที่มี Sales ไม่ได้รับยอดเงิน/%GP เลย · ถ้าตั้ง webhook ของกลุ่มภายในให้ชี้ไปกลุ่มที่มี Sales (ตั้งผิด) ข้อความภายในจะถูกระงับ ไม่หลุดไปให้ Sales
- `LARK_WEBHOOK_URL` ตัวเดิม (v4.7) ยังใช้ได้ แต่ใช้แทนได้เฉพาะกลุ่มภายใน (Sourcing / ผู้อนุมัติ)

### สร้าง webhook ในแต่ละกลุ่ม
1. เปิดกลุ่มใน Lark → ⚙ Settings → **Bots** → **Add Bot** → **Custom Bot** → ตั้งชื่อ เช่น `MGS Pricing`
2. คัดลอก **Webhook URL** (`https://open.larksuite.com/open-apis/bot/v2/hook/…`)
3. **Security settings** → เปิด **Signature verification** → คัดลอก **Secret** (ไม่ต้องตั้ง keyword / IP)
4. Apps Script → ⚙ Project Settings → **Script Properties** → เพิ่ม `LARK_WEBHOOK_<กลุ่ม>` = URL และ `LARK_WEBHOOK_<กลุ่ม>_SECRET` = Secret
5. ใส่ `APP_URL` = ลิงก์ `/exec` ของเว็บแอป และ `LARK_MODE` = `dryrun`
6. รัน `larkCheckConfig` (หรือเปิด `…/exec?diag=1`) → ไม่มี ✗ · อ่านคำเตือนว่ากลุ่มไหนจะถูกข้าม/ระงับ
7. รัน `larkInstallTriggers` → ใช้งาน 1–2 วัน ดูแท็บ `NotifyQueue` → พร้อมแล้วเปลี่ยน `LARK_MODE` = `live`

## 1. ตาราง event (ที่เดียวในโค้ด: `LARK_EVENTS` ใน `Lark.gs`)

| Event | เกิดเมื่อ | ส่งถึง | หัวการ์ด | ข้อมูลในการ์ด | ปุ่ม (ลิงก์ตรงไปเอกสาร) | กันส่งซ้ำ |
|---|---|---|---|---|---|---|
| `SR_SUBMITTED` | Sales ส่งคำขอราคา (SR) ใหม่ / ส่งร่างที่ค้างไว้ | ทีม Sourcing + กลุ่มคำขอราคา | 🆕 คำขอราคาใหม่เข้าคิว · เลข SR | โครงการ · ลูกค้า · Sales · จำนวนรายการ · ต้องการราคาภายใน · โดย | เปิดคำขอราคา → ระบบทำราคา | 24 ชม. / SR |
| `QT_SUBMITTED` | Sourcing กด “บันทึก & ส่งขออนุมัติ” | ผู้อนุมัติราคา | 🧾 ใบเสนอราคารออนุมัติ · เลข QT | โครงการ · ลูกค้า · Sales · มูลค่า · **%GP** · รอบ · โดย | เปิดเพื่ออนุมัติ → ระบบทำราคา | 2 ชม. / ใบ / รอบ |
| `QT_APPROVED` | ผู้อนุมัติครบทุกฝ่าย (หรือ GM อนุมัติแทน) | ทีม Sourcing + ผู้ปล่อยราคา | ✅ อนุมัติราคาครบแล้ว · รอปล่อยราคา | โครงการ · ลูกค้า · Sales · มูลค่า · รอบ · โดย | Sourcing → ระบบทำราคา · ผู้ปล่อยราคา → แอป Sales | 24 ชม. / ใบ / รอบ |
| `QT_RETURNED` | ผู้จัดการส่งใบที่รออนุมัติกลับไปแก้ (ไม่อนุมัติ) | ทีม Sourcing | ↩️ ไม่อนุมัติ · ส่งกลับแก้ราคา | โครงการ · ลูกค้า · Sales · มูลค่า · โดย · หมายเหตุ “ต้องขออนุมัติใหม่ทั้งสองฝ่าย” | เปิดใบเสนอราคา | 2 ชม. / ใบ / รอบ |
| `PRICE_RELEASED` | ผู้ปล่อยราคากดปล่อยราคาให้ Sales | ทีมขาย + กลุ่มคำขอราคา | 📤 ปล่อยราคาแล้ว · พร้อมเสนอลูกค้า | โครงการ · ลูกค้า · Sales · โดย — **ไม่มียอดเงิน/GP** (ให้กดเปิดดูราคาในแอป) | เปิดในแอป Sales | 24 ชม. / ใบ / รอบ |
| `SLA_BREACH` | ตรวจทุกชั่วโมง: งานรอเกินวันทำการที่กำหนด | กลุ่มของผู้รับผิดชอบงานตอนนั้น | ⛔ งานเกินกำหนด (SLA) · ชื่อกลุ่ม | จำนวนงานที่เพิ่งเกิน + รายการ (รอนานสุดก่อน สูงสุด 10) | เปิดระบบ | **การ์ดเดียวต่อกลุ่มต่อรอบ** · งานเดิมไม่แจ้งซ้ำใน 24 ชม. |
| `DAILY_DIGEST` | ทุกเช้าวันทำการ 08:30 | ทุกกลุ่มที่มีงานค้าง | 📋 สรุปงานค้างประจำวัน · ชื่อกลุ่ม | งานค้างทั้งหมด · ⛔ เกินกำหนด · ⚠ เฝ้าระวัง + รายการ (แย่สุดก่อน) | เปิดระบบ | **1 การ์ด / กลุ่ม / วัน** · ไม่มีงาน = ไม่ส่ง |

ผู้รับผิดชอบงาน → กลุ่ม: Sourcing (และงานซ่อมข้อมูล) → ทีม Sourcing · ผู้จัดการ → ผู้อนุมัติราคา · ผู้ปล่อยราคา → ผู้ปล่อยราคา · Sales → ทีมขาย

ตัวอย่าง payload การ์ดจริงของทุก event: [`lark_payload_samples.json`](lark_payload_samples.json) (สร้างจากโค้ดจริงโดย `tests/test_v47.js`)

## 2. โครงสร้าง (สร้างข้อความ ↔ ส่ง แยกกัน)

```
บันทึก/อนุมัติ/ปล่อยราคา (Code.gs, ใต้ ScriptLock)
   └─ larkHook_()  → larkOnStatus_() → larkEventFor_()  เลือก event จากการเปลี่ยนสถานะ (pure)
                     └─ larkEnqueue_()  สร้างการ์ด (larkBuild_ — pure) + ตัดตัวซ้ำ + เขียนแท็บ NotifyQueue 1 ครั้ง
                         (ไม่ยิง HTTP ในธุรกรรมหลัก · ผิดพลาด = บันทึก Log แต่การบันทึกเอกสารสำเร็จเสมอ)
trigger ทุก 5 นาที → larkFlush()   จองแถว → fetchAll ครั้งเดียว → เขียนผลครั้งเดียว
                                    ล้มเหลว → RETRY (1 / 5 / 15 / 60 / 180 นาที) → ครบ 5 ครั้ง = FAILED + Log “lark-failed”
trigger ทุกชั่วโมง → larkSlaScan()     · ทุกเช้า 08:30 → larkDailyDigest()
```

สถานะในแท็บ `NotifyQueue`: `PENDING` รอส่ง · `SENDING` กำลังส่ง · `SENT` ส่งแล้ว · `DRYRUN` สร้างแล้วแต่ไม่ส่ง (โหมด dry-run) · `RETRY` รอลองใหม่ · `FAILED` ลองครบแล้วไม่สำเร็จ · `SKIPPED` ไม่มีปลายทางของกลุ่มนั้น · `GROUPED` งาน SLA ที่รวมอยู่ในการ์ดสรุปแล้ว (ใช้กันแจ้งซ้ำ)

## 3. ความปลอดภัย

- Credential อยู่ใน **Script Properties** เท่านั้น (ไม่อยู่ในโค้ด/ชีท) · หน้า `?diag=1` และ `larkCheckConfig()` แสดงแบบปิดบัง
- การ์ดถึงทีมขายไม่มีต้นทุน/GP · การ์ดถึงผู้อนุมัติมี %GP แต่ไม่มียอดต้นทุน/กำไรเป็นเงิน → กลุ่ม `LARK_CHAT_APPROVERS` ต้องมีเฉพาะผู้จัดการ
- ข้อความจากผู้ใช้ (ชื่อโครงการ/ลูกค้า) ถูกตัด `< >` และอักขระควบคุม — กัน `<at user_id="all">` ปลุกทั้งกลุ่ม · ใช้ `plain_text` ทั้งหมด
- ปุ่มเปิดเอกสารยังผ่านการล็อกอินและตรวจสิทธิ์ตามปกติ (Sales ที่ไม่ใช่เจ้าของงานกดลิงก์ก็ไม่เห็นราคา)
- คำขอ Bot API ส่ง `uuid` = Id ของแถวในคิว → Lark ไม่แสดงซ้ำแม้ระบบลองส่งใหม่

## 4. ตั้งค่า (Project Settings → Script properties)

| Property | ค่า | จำเป็น |
|---|---|---|
| `LARK_MODE` | `dryrun` (รอบนี้) → `live` เมื่อพร้อม · `off` = ปิด | แนะนำให้ตั้ง (ไม่ตั้ง = dryrun) |
| `LARK_DOMAIN` | `https://open.larksuite.com` หรือ `https://open.feishu.cn` | ไม่ (ค่าเริ่มต้น larksuite) |
| `LARK_APP_ID` / `LARK_APP_SECRET` | ของ Custom App ที่เปิด Bot + สิทธิ์ `im:message:send_as_bot` | ตอน live |
| `LARK_CHAT_SOURCING` / `LARK_CHAT_APPROVERS` / `LARK_CHAT_RELEASE` / `LARK_CHAT_SALES` | chat_id (`oc_…`) ของแต่ละกลุ่ม (เพิ่ม Bot เข้ากลุ่มก่อน) · RELEASE ไม่ตั้ง = ใช้กลุ่ม SALES | ตอน live |
| `LARK_WEBHOOK_URL` / `LARK_WEBHOOK_SECRET` | Custom Bot webhook — ข้อความธรรมดาเข้ากลุ่มเดียว (สำรอง ถ้ายังไม่มี App) | ไม่ |
| `APP_URL` | URL `/exec` ของ Web App (ไม่ตั้ง = ใช้ URL ของ deployment ปัจจุบัน) | แนะนำ |

## 5. ขั้นตอน

**รอบนี้ (dry-run)**
1. เพิ่มไฟล์ `Lark.gs` + วาง `Code.gs` / `Index.html` / `Sales.html` ใหม่ → รัน `setup()` (สร้างแท็บ `NotifyQueue` + ตรวจการตั้งค่า)
2. รัน `larkDryRunDemo()` ใน Editor → ดู payload ทุก event ใน Execution log (ไม่เขียนชีท ไม่ยิง HTTP)
3. (ทางเลือก) รัน `larkInstallTriggers()` → ใช้งานจริงตามปกติ 1–2 วัน แล้วเปิดแท็บ `NotifyQueue` ดูว่าข้อความที่ “จะ” ส่ง ถูกคน ถูกจังหวะ ไม่ถี่เกินไหม (ทุกแถวเป็น `DRYRUN`)

**เปิดส่งจริง (ภายหลัง เมื่อยืนยันแล้ว)**
1. สร้าง Custom App ใน Lark Developer Console → เปิด Bot → ให้สิทธิ์ส่งข้อความ → เพิ่ม Bot เข้า 3–4 กลุ่ม → จด chat_id
2. ตั้ง Script Properties ตามตารางข้อ 4 → เปิด `?diag=1` ต้องไม่มี ✗
3. ตั้ง `LARK_MODE` = `live` → ข้อความใหม่จะเริ่มส่งในรอบ trigger ถัดไป (แถว `DRYRUN` เก่าจะไม่ถูกส่งย้อนหลัง)
4. ปิดฉุกเฉิน: ตั้ง `LARK_MODE` = `off` (ไม่ต้อง deploy ใหม่)

เครื่องมือใน Editor: `larkCheckConfig()` · `larkDryRunDemo()` · `larkQueueReport(20)` · `larkInstallTriggers()`
